小而实用的功能

表大小与表数量限制

面向多租户、临时及演示服务的硬性限制：

CREATE TABLE t (…) ENGINE = MergeTree ORDER BY id SETTINGS max_table_size_rows = 1000000; -- also max_table_size_bytes_compressed, ..._uncompressed INSERT INTO t … -- Table size limit exceeded: ... 1200000, which exceeds -- the 'max_table_size_rows' setting value (1000000). CREATE DATABASE tenant ENGINE = Atomic SETTINGS max_tables = 100; -- Too many tables in database `tenant`. (TOO_MANY_TABLES)

— 在 INSERT 开始时及数据分片提交时检查。
— 表、视图和字典均计入 max_tables.

开发者：Alexey Milovidov。

Merge 表支持并行副本

现在可以使用并行副本读取 Merge 表，
而且其上层聚合也会分布式执行：

CREATE TABLE logs_all ENGINE = Merge(default, '^logs_'); SELECT toYear(d), count() FROM logs_all GROUP BY 1 SETTINGS enable_parallel_replicas = 1, parallel_replicas_plan_based = 1, parallel_replicas_allow_merge_tables = 1; EXPLAIN: ReadFromParallelReplicas (Aggregating Union: ReadFromMergeTree (logs_2025), (logs_2026))

— 将 Merge 展开为 MergeTree 读取的并集，
  然后分发执行计划；副本无需处理 Merge 专有逻辑。
— 使用 FINAL 或非 MergeTree 子表时，回退为单副本执行。

开发者：Igor Nikonov。

线性回归聚合函数

符合 SQL 标准的函数族，共九个：

SELECT regr_slope(y, x), regr_intercept(y, x), regr_r2(y, x), regr_count(y, x) FROM VALUES('x Float64, y Float64', (1, 3.1), (2, 4.9), (3, 7.2), (4, 8.8), (5, 11.1)); -- 1.99 │ 1.05 │ 0.9973 │ 5 — y ≈ 2x + 1

— 还包括 regr_avgx、regr_avgy、regr_sxx、regr_syy、regr_sxy。
— 名称与 PostgreSQL、Oracle、Snowflake 中相同，
  查询可原样迁移。
— 组合器、GROUP BY 与窗口函数照常适用。

开发者：mosya415。

JSON 子列的方括号语法

现在可以像访问映射键一样访问 JSON 列中的路径：

SELECT json['user']['name'], json['tags'] FROM events; -- the same as json.user.name and json.tags SELECT json['user.name'], json['first name'] FROM events; -- keys with dots and spaces — without backticks

— 解析器会将其转换为嵌套的 arrayElement 调用；
  得到的仍是同一个 Dynamic 子列。

— 使用过 Map 列的用户会很熟悉这种写法。

开发者：Pavel Kruglov。

arrayFlattenedLength

嵌套数组在所有层级一共有多少个元素？

SELECT arrayFlattenedLength([[1, 2], [3], [4, 5, 6]]), length([[1, 2], [3], [4, 5, 6]]); -- 6 │ 3

— 效果相当于 length(arrayFlatten(arr))，但不需要物化展平后的数组。

— 与 PostgreSQL 的 cardinality 一样，会统计每个层级；
  ClickHouse 的 cardinality 则是 length 的别名，只统计最外层数组。

开发者：David Meng。

system.statements

每条 SQL 语句的文档现在都可从服务器内部获取：

SELECT syntax FROM system.statements WHERE name = 'SELECT';

— 列包括 name、syntax、description、parent_name、related。

— 与文档渲染使用相同的数据源，始终与当前二进制程序匹配。

— 与 system.functions、system.settings、system.formats 等系统表并列。

演示

开发者：Robert Schulze。

system.session_query_ids

“我刚运行了哪些查询？”无需手动指定 ID：

SELECT count() FROM numbers(10); SELECT sum(number) FROM numbers(100); SELECT query, query_duration_ms FROM system.query_log WHERE query_id IN (SELECT query_id FROM system.session_query_ids) AND type = 'QueryFinish' ORDER BY event_time_microseconds; -- SELECT count() FROM numbers(10) │ 234 -- SELECT sum(number) FROM numbers(100) │ 112

— 按执行顺序列出当前会话的查询 ID。
— 适用于测试和基准测试脚本；记录数量受
  session_query_ids_history_size（默认 1000）限制；TRUNCATE 可清空记录。

演示

开发者：Vladimir Cherkasov。

无需 Keeper 协调的 S3Queue

S3Queue 新增第三种模式，适用于单台执行摄取的服务器：

CREATE TABLE queue (WatchID UInt64, URL String, EventDate Date) ENGINE = S3Queue('s3://bucket/landing/*.parquet', NOSIGN, 'Parquet') SETTINGS mode = 'exclusive'; CREATE MATERIALIZED VIEW mv TO events AS SELECT * FROM queue;

— unordered 和 ordered 会在 Keeper 中跟踪每个文件，
  因而多台服务器可以共享同一个队列。

— exclusive 在服务器内存中跟踪文件：每个文件无需
  再与 Keeper 往返通信；适用于仅由这台服务器处理的存储桶。

开发者：Ivan Tkatchev。

性能
改进

从列统计信息计算 min、max、count

列统计信息（自 26.4 起默认启用）保存每个数据片段中每个数值类列的精确最小值和最大值。
聚合现在可直接读取这些统计信息：

SELECT min(EventDate), max(EventDate), count() FROM hits; -- no data is read, answered from statistics EXPLAIN: Aggregating └── ReadFromPreparedSource (_statistics_min_max_projection)

示例：26.8：8–24 毫秒。   26.9：2 毫秒。

— 没有统计信息的数据片段仍按常规方式读取并合并结果。
— 设置：use_statistics_for_min_max_aggregation。

开发者：Alexey Milovidov。

插入时跳过空列

对于大多数插入操作中大部分列都为空的宽表：
不再将这些空值写入存储。

CREATE TABLE wide (id UInt64, a String, b UInt64, c Array(UInt32), j1 JSON, j2 JSON) ENGINE = MergeTree ORDER BY id SETTINGS skip_empty_columns_on_insert = 1, serialization_info_version = 'with_missing_columns'; INSERT INTO wide (id, a, j1) … -- b, c, j2 are all defaults in this block -- serialization.json: "missing_columns": [{"name":"b","type":"UInt64"}, ...] -- files in the part: 49 → 33; no data streams at all for b, c, j2

— 读取时根据记录的类型重建默认值；该标记
  在合并、变更、复制和备份后仍会保留。
— 需主动启用：滚动升级期间请继续使用旧版序列化格式。

开发者：Amos Bird。

更快的 Native 协议

每次查询结束时，服务器都会连续发送一批很小的消息：
概要信息、进度、ProfileEvents、数据流结束标记等。

以前每条消息都占用一个 TCP 数据包：

$ tcpdump -i lo 'tcp src port 9000' # SELECT 1, server -> client 26.8: 23 10 10 3133 14 10 1 - 7 packets 26.9: 23 3278 - 2 packets

— 空闲一段时间后，Linux 会缩小拥塞窗口；
  若突发消息量超过窗口，就必须等待 ACK，增加整整一次网络往返。

在延迟 30 毫秒的链路上，查询间存在空闲的客户端延迟此前约翻倍。

— 现在查询结束消息通过一次套接字写入发出。

开发者：Kaviraj Kanagaraj。

文本索引支持 LIKE 和 ILIKE

自 26.7 起，文本索引可通过扫描字典处理 %word%。
现在也支持前缀和后缀模式：

SELECT count() FROM docs WHERE body LIKE 'clickhouse%'; -- startsWith SELECT count() FROM docs WHERE body LIKE '%clickhouse'; -- endsWith EXPLAIN indexes = 1: Prewhere: endsWith(body, 'clickhouse') AND __text_index_idx_endsWith_… Skip: Name: idx, Granules: 4/2442

— 索引提供的是提示：倒排列表选出数据粒度，
  再由原始条件重新检查各行。
— LIKE … ESCAPE 现在可使用文本、ngram、token 和 sparse-gram 索引。
— array 分词器可处理任意 LIKE/ILIKE 模式。

开发者：Elmi Ahmadov。

AArch64 上的性能提升

Graviton、Ampere、Apple、NVIDIA Grace — 一批专门针对 ARM 的修复：

— memcpy：字符串、连接和读取路径中的小规模复制辅助函数
  在 AArch64 上会被编译成 libc 的 memcpy 调用 — 恰恰是该函数本来要避免的调用。
  2024 年已修复 x86 上的问题；现在 ARM 上也会内联。
— 过滤器：使用 NEON 寄存器累加优化底层 WHERE 处理，
  最高可加快 15 倍。
— 此外，T64 编解码器、128 位除法和 UTF-8 验证也得到加速。

示例：在 Graviton3 上单线程对 1 亿个短字符串执行 DISTINCT：

26.8：12.4 秒。   26.9：7.6 秒。

开发者：Joshua Dorst、Harikrishnan Prabakaran。

更快的 k 路合并

合并有序数据流是 MergeTree 的核心，涵盖合并、FINAL、
ORDER BY 和 optimize_on_insert。以下是三项 k 路合并优化：

— 多列排序键和带排序规则的键：改用有序游标数组
  而非堆，快 7–8%。

— 互不交叠的数据片段（按时间顺序插入）：通过 O(1) 次比较，
  将整个游标识别为一个批次。

— 跳过连续重复的键：ReplacingMergeTree 的 FINAL
  最多减少 40% 的 CPU 用量，optimize_on_insert 去重约快 3 倍。

Maksim Kita 的博文介绍了这些思路及其原理。

开发者：Alexey Milovidov。

ARRAY JOIN 后使用索引

针对 ARRAY JOIN 元素的条件现在可驱动跳数索引分析，
与现有的 arrayJoin(col) IN (…) 一样：

CREATE TABLE t (id UInt64, tags Array(String), INDEX bf tags TYPE bloom_filter) … SELECT count() FROM t ARRAY JOIN tags AS tag WHERE tag IN ('rare7', 'rare8'); -- 26.8: Granules 1223/1223 — full scan -- 26.9: Skip bf — Granules 2/1223

— arrayJoin 现在内部会规划为 ARRAY JOIN 运算符。
— 对元素的 WHERE 条件会在展开之前应用：
  不匹配的元素不会成为行。

开发者：Yarik Briukhovetskyi。

更快地从对象存储读取子列

一个 JSON 列可能包含数百条子数据流；此前在 S3 上，
系统逐条加载它们的标记，每条都需要一次网络往返：

-- github.com/ClickHouse/datasets, attached from R2 as a plain_rewritable disk: ATTACH DATABASE datasets UUID 'e053c139-f7b8-4c82-acb7-6b259c5b19e8' ENGINE = Atomic SETTINGS disk = disk(type = 's3_plain_rewritable', endpoint = 'https://data.clickhouse.com/public-datasets/db/', no_sign_request = true, readonly = true), lazy_load_tables = true; SELECT data.wiki.:String AS wiki, count() AS edits FROM datasets.wikipedia_edits WHERE time >= now() - INTERVAL 1 DAY AND data.type.:String = 'edit' GROUP BY wiki ORDER BY edits DESC LIMIT 5; -- data is a JSON column

示例：26.8：8.3 秒，1733 次请求，235 个连接。
26.9：6.3 秒，1512 次请求，59 个连接。

— 默认以异步、并行方式加载所有数据流的标记；
  不加载空数据流的标记；JSON 元数据只读取一次。

开发者：Alexey Milovidov、Rory Shanks、Pavel Kruglov。

更充分地复用对象存储连接

此前版本中，读取到文件末尾的连接
会继续被占用，而不会归还连接池。

这造成不必要的额外连接和频繁的 TLS 握手。

-- one row of the bluesky_car_records JSON column, 4723 substreams: 26.8: 29,714 connections created — over the hard limit of 25,000: Cannot create new connection to data.clickhouse.com:443 26.9: 2,885 connections, 265,563 reused -- wikipedia_edits, edits per wiki (Compact parts): 235 → 59 connections

— 在 26.9 中，后续请求能更充分地复用连接。

连接重排序中的冲突检测器

对于 SEMI、ANTI 和 OUTER 连接，哪些连接顺序有效？
此前每个非内连接都是一道障碍：即使 SEMI 连接具有很高的过滤选择性，
也必须固定在为其提供输入的内连接之上。

SET query_plan_optimize_join_order_algorithm = 'dpsub', query_plan_optimize_join_order_use_conflict_detector_c = 1; EXPLAIN SELECT count() FROM big1 JOIN big2 ON big1.k = big2.k LEFT SEMI JOIN small ON big1.k = small.k; -- before: (big1 ⋈ big2) ⋉ small -- 10M ⋈ 10M first, then filter -- after: big2 ⋈ (big1 ⋉ small) -- the 1000-row semi join goes first

— 使用 SIGMOD'13 论文 《论核心搜索空间的正确且完整
  枚举》中的 CD-A 和 CD-C 冲突检测器 — 这是当前最先进的方法。

开发者：Fisnik Kastrati。

更快的递归 CTE

递归 CTE 的每一步都会将结果写入一个中间
Memory 表，再由下一步读取 — 每个数据块对应一块存储：

WITH RECURSIVE frontier AS ( SELECT 1 AS node, 0 AS depth UNION ALL SELECT e.dst, depth + 1 FROM edges e JOIN frontier f ON e.src = f.node WHERE depth < 6) SELECT count() FROM frontier;

— 由大量按数据粒度大小读取（或 ARRAY JOIN
  展开）组成的图搜索，以前每一步都会积累数千个微小数据块。
— 现在写入前会先合并小块，与普通 INSERT 一样。

开发者：Zach Naimon。

更快的 uniq 和 uniqCombined

按分组进行近似去重计数 — 每个
“每页独立用户数”查询都是这种形式：

SELECT URL, uniq(UserID) FROM hits GROUP BY URL; SELECT k, uniqCombined64(v) FROM t GROUP BY k;

— 当大量分组交错出现时，每行都会落入不同的状态，
  访问每个状态内部的哈希集合都会造成缓存未命中。
— 现在先计算一批数据的哈希值，再把目标单元格
  预取到缓存 — 把聚合器自身的技巧用到各个状态内部。
— 此外：对聚合状态、JSON 和 Variant 求哈希时，无需逐行
  复制缓冲区 — 200 字节状态的 uniqExact 提速 33%。

开发者：Manuel。

JOIN：按行存储哈希表载荷

哈希连接的右侧按列存储；构建输出时，
必须为每个匹配行逐列获取一个值。

before: col1 Int32 │ col2 String │ col3 UInt8 │ col4 Float64 — 4 gathers per row after: ROW STORE (col1 + col3 + col4, contiguous per row) col2 String (columnar) ┌──────┬──────┬────────┐ │ col1 │ col3 │ col4 │ <- row N: one pointer, one copy └──────┴──────┴────────┘

— 固定大小的列被打包成行式存储，默认开启
  （enable_hash_join_row_store）。
— 不选择任何右侧列的 LEFT SEMI / ANTI 连接会构建仅含键的
  哈希表，并释放右侧数据块 — 最多提速 1.5 倍，内存减半。

示例：100M × 30M 的 LEFT SEMI JOIN：26.8：0.50 秒。   26.9：0.37 秒。

开发者：Hechem Selmi、Nikita Taranov。

GROUP BY：三项小改进

— 不含聚合函数的 GROUP BY 曾在更高基数时才开始预取，

  query_plan_aggregation_bucket_top_k。

有趣的内容

带边界条件的 LIMIT

按行在数据流中满足条件的位置选取，而不是按固定序号：

SELECT number FROM numbers(10) ORDER BY number LIMIT 3 AFTER number >= 5; -- 5, 6, 7 SELECT number FROM numbers(10) LIMIT UNTIL number >= 3; -- 0, 1, 2 SELECT number FROM numbers(10) LIMIT AFTER number >= 2 UNTIL number >= 6; -- 2, 3, 4, 5 SELECT number FROM numbers(10) LIMIT 2 AFTER number IN (2, 6) ALL; -- 2, 3, 6, 7

— “从第一次错误到下一个检查点” — 一次扫描即可完成，
  无需窗口函数或客户端截取。
— AFTER 包含边界，UNTIL 不包含边界；
— 条件可以引用未被选出的列。

开发者：Zakhar Kravchuk、Nihal Miaji。

可溢写到外存的 DISTINCT

DISTINCT 会为所有键维护一个哈希集合 — 基数高时会耗尽内存。
现在它会像 GROUP BY 和 ORDER BY 一样溢写到磁盘：

SELECT count() FROM (SELECT DISTINCT number FROM numbers_mt(300000000)) SETTINGS max_memory_usage = 3000000000; -- 26.8: Query memory limit exceeded (MEMORY_LIMIT_EXCEEDED) SET max_bytes_before_external_distinct = 1000000000; -- default: max_bytes_ratio_before_external_distinct = 0.5

示例，300M 个不同键：内存中：12.9 GB，12.3 秒。
在 1 GB 时溢写：1.14 GB，12.1 秒。 — 速度相当，内存用量仅约十分之一。

— 默认开启。磁盘上采用有序游程，并在每个阶段去重。
— ORDER BY 之后的 DISTINCT 在溢写时会保留排序顺序。

开发者：Nihal Z. Miaji。

按认证方式限定授权

一个用户、多组凭据 — 每组都有自己的权限限制：

ALTER USER app ADD IDENTIFIED WITH sha256_password BY 'readonly_key' VALID FOR INTERVAL 30 DAY GRANTS (SELECT ON default.sales); -- a session authenticated with readonly_key: SELECT count() FROM default.sales; -- 1000 INSERT INTO default.sales VALUES (1, 'x', 1); -- ACCESS_DENIED

— 会话权限 = 用户授权与列表的交集。
  此子句绝不增加权限。
— 权限绑定到用户：在 query_log 中仍显示为该用户；
  用户被删除时认证会遭拒绝；
  用户失去授权时权限范围也会缩小。

开发者：Alexey Milovidov。

由服务器为当前用户生成供应用使用的令牌：

REFRESH … APPEND INCREMENTAL

可刷新物化视图可以只处理上次刷新后
提交到来源表的新行：

CREATE TABLE src (ts DateTime, k UInt32, v UInt64) ENGINE = MergeTree ORDER BY ts SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1; CREATE MATERIALIZED VIEW hourly REFRESH EVERY 1 HOUR APPEND INCREMENTAL ENGINE = MergeTree ORDER BY k AS SELECT k, sum(v) AS s, count() AS c FROM src GROUP BY k;

— 游标是来源表的块编号 — 因此需要上述两项设置。

— 介于逐次插入处理的增量物化视图与完整刷新之间：
  按计划从来源表获取增量。

开发者：Smita Kulkarni。

增量复制到 Iceberg

可刷新物化视图可以只处理上次刷新后
提交到来源表的新行：

CREATE TABLE src (ts DateTime, k UInt32, v UInt64) ENGINE = MergeTree ORDER BY ts SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1; CREATE MATERIALIZED VIEW hourly REFRESH EVERY 1 HOUR APPEND INCREMENTAL ENGINE = MergeTree ORDER BY k AS SELECT k, sum(v) AS s, count() AS c FROM src GROUP BY k;

一个用例：将 MergeTree 表复制到 Iceberg。

追加到 Iceberg 目标表具备恰好一次语义：游标存放在快照中。

PromQL：私有预览

TimeSeries 引擎、PromQL 方言和 timeSeries* 函数
已从实验性功能升至私有预览 — 可直接替代 Prometheus：

SET dialect = 'promql', promql_database = 'default', promql_table = 'metrics'; sum by (status) (rate(http_requests_total[5m])) -- [('status','500')] │ 2026-09-17 00:56:28.000 │ 1.245 -- or from SQL, with a time range and a step: SELECT tags, samples FROM prometheusQueryRange(default.metrics, 'sum by (status) (rate(http_requests_total[5m]))', now() - INTERVAL 1 HOUR, now(), INTERVAL 5 MINUTE);

— 对 PromQL 的覆盖率超过 85%，且严格遵循 Prometheus 语义；26.9 新增 absent、
  count_values、*_over_time、predict_linear，以及从 TimeSeries 表执行 SELECT。
— 博客：ClickHouse 全新 TimeSeries 引擎简介。

开发者：Vitaly Baranov、Nikita Mikhaylov、Valery Petrov、Minh Vu。

实验性功能

重新实现 Kusto 查询语言 🧪

KQL 方言于 2022 年由社区贡献，此后停滞不前：它将词法单元转换为
SQL 文本后重新解析，
还注册了 28 个实际不起作用的函数。

SET dialect = 'kusto', allow_experimental_kusto_dialect = 1; print q = 7 / 2, sub = substring('abcdefg', -3, 2), c = '50x' contains '50%' -- before: 3.5 │ 'ab' │ true (the needle was pasted into a LIKE pattern) -- now: 3 │ 'ef' │ false — what Kusto returns

— 现在采用专用的词法分析器、语法分析器和 AST 转换。

开发者：Alexey Milovidov。

Trino SQL 方言 🧪

为 Trino（以及 Presto、Athena）编写的查询现在可以原样运行：

SET dialect = 'trino', enable_trino_dialect = 1; SELECT x, TRY_CAST('abc' AS INTEGER) AS c, cardinality(ARRAY[1, 2, 3]) AS n FROM UNNEST(ARRAY[10, 20, 30]) AS t(x) OFFSET 1 LIMIT 5; -- 20 │ NULL │ 3 / 30 │ NULL │ 3 SELECT transform(ARRAY[1, 2, 3], x -> x * 2), approx_percentile(v, 0.9), date_trunc('month', TIMESTAMP '2026-09-17 10:00:00'), ROW(1, 'a') FROM (VALUES (1), (2), (3), (10)) AS t(v); -- [2,4,6] │ 10 │ 2026-09-01 │ (1,'a')

— 无需单独的语法：使用词法单元级语法转换、标准语法分析器，
 以及约 340 个 Trino 函数的 AST 级映射（包括重命名、将 lambda 参数移到最后）。

开发者：Alexey Milovidov、Ethan Lin。

数据湖

创建新的 Delta Lake 表

ClickHouse 自 23.x 起支持读取 Delta Lake，自 26.2 起支持写入 — 现在还可以
从零开始创建表：

SET allow_delta_lake_writes = 1, allow_delta_lake_create_table = 1; CREATE TABLE trips (id Int64, name String, score Float64) ENGINE = DeltaLake('s3://bucket/warehouse/trips/', '<key>', '<secret>'); INSERT INTO trips VALUES (1, 'a', 1.5), (2, 'b', 2.5); -- _delta_log/00000000000000000000.json: -- {"commitInfo":{"operation":"CREATE TABLE","engineInfo":"ClickHouse",...}}

— 还可附加到现有 _delta_log，或注册到 Unity 目录。支持 S3、Azure 和本地存储。

开发者：Smita Kulkarni。

并行解码 Iceberg 清单

规划 Iceberg 查询时需要遍历清单：获取清单、解析 Avro，
再按分区和最小／最大值裁剪每个条目。此前整个遍历过程串行执行。

— 26.8 预取下一份清单 — 仅获取阶段可重叠。
— 26.9 并发解码清单，并将裁剪后保留的条目流式送入
 带背压的有界队列。

PR 中的示例：18 份数据清单，113 MB，约 7.5 万个条目：

串行：8.45 秒。   4 线程：2.55 秒。   16 线程：1.68 秒。

— 由 iceberg_manifest_decode_concurrency（默认 4）限制并发数。

开发者：Aaron Harlap。

利用 Iceberg 清单列表裁剪

清单列表包含每份清单的分区摘要：lower_bound、
upper_bound、contains_null。现在打开清单前就可据此裁剪整份清单：

CREATE TABLE ice (id Int64, m UInt32, d Date, v Float64) ENGINE = Iceberg(…) PARTITION BY m; -- 8 inserts, one month each SELECT count() FROM ice WHERE m = 5; -- metadata files read: 41 -> 7 (use_iceberg_manifest_list_partition_pruning) -- data files listed: 39 -> 5 (per-entry partition pruning, as before)

— 现在有三个裁剪层级：清单列表、清单条目、Parquet 行组。
— 自 26.9 起，ClickHouse 也会将分区摘要写入清单列表。

开发者：Konstantin Vedernikov。
