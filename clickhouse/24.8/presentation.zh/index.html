默认多查询模式

在 clickhouse-client 和 clickhouse-local 中：

24.7:

$ clickhouse-local -q "SELECT 1; SELECT 2;" Code: 62. DB::Exception: Syntax error (Multi-statements are not allowed): failed at position 9 (end of query): ; SELECT 2;. . (SYNTAX_ERROR) $ clickhouse-local --multiquery "SELECT 1; SELECT 2;" 1 2 $ clickhouse-local -n "SELECT 1; SELECT 2;" 1 2

24.8:

$ clickhouse-local --query "SELECT 1; SELECT 2;" 1 2 $ ch "SELECT 1; SELECT 2;" 1 2

支持包含 INSERT 和 SELECT 查询的复杂 SQL 脚本。

开发者：FFish。

虚拟列 _etag

:) SELECT _path, _etag FROM s3('s3://ookla-open-data/parquet/performance/**') LIMIT 10

ETag 是用于缓存的 HTTP 资源标识响应头。

在 S3 中，它通常是对象内容的弱哈希（MD5），
但也可能取决于对象上传方式。

已在 S3、Azure 和 HDFS 中实现。

开发者：Skyoct。

Hive 风格分区

将数据划分到不同目录的分区方式，
对象路径包含以下形式的子目录： key=value.

示例： 

s3://ookla-open-data/parquet/performance/type=fixed/year=2019/quarter=1/
2019-01-01_performance_fixed_tiles.parquet

ClickHouse 24.8:

SET use_hive_partitioning = 1;

— 启用虚拟列 type, year, quarter
  并自动推断其类型。

开发者：Yarik Briukhovetskyi。

带标签的查询缓存

SET use_query_cache = 1, query_cache_tag = 'abc';

不同 query_cache_tag 的查询将分别缓存。

使用场景：把特定结果保存到缓存供后续访问，
不影响其他查询。

不同用户的缓存默认已隔离，
关键设置不同的查询也分别缓存。

开发者：Sakulali。

合并期间的投影控制

ClickHouse 表可包含“投影”， — 以不同物理顺序或聚合形式表示相同数据，使查询能自动利用这些数据优化执行。

CREATE TABLE hits (CounterID UInt32, URL String, ... PROJECTION totals (SELECT CounterID, count(), uniq(URL) GROUP BY CounterID) ) ENGINE = MergeTree ORDER BY (CounterID, EventTime);

在进行非简单的后台合并时，
例如 ReplacingMergeTree, AggregatingMergeTree 等引擎，
以及执行 OPTIMIZE table DEDUPLICATE 查询时，会发生什么？

24.8 之前，投影会与主数据失去同步。

开发者：ShiChao Jin。

合并期间的投影控制

在进行非简单的后台合并时，
例如 ReplacingMergeTree, AggregatingMergeTree 等引擎，
以及执行 OPTIMIZE table DEDUPLICATE 查询时，会发生什么？

24.8 之前，投影会与主数据失去同步。

从 24.8 起，由新的表级设置控制： 

deduplicate_merge_projection_mode = 'throw'/'drop'/'rebuild'

从 24.7 起，我们还提供控制轻量删除行为的设置：lightweight_mutation_projection_mode。

开发者：ShiChao Jin。

新的 Kafka 引擎 🧪

这个 Kafka 引擎自 2017 年起存在于 ClickHouse，
— 实现从 Kafka 流式消费及构建数据流水线。

其缺点是：向 Kafka 与 ClickHouse 提交并不原子，重试时可能产生重复数据。

现在可选择在 Keeper 中管理偏移量：

SET allow_experimental_kafka_offsets_storage_in_keeper = 1; CREATE TABLE ... ENGINE = Kafka( 'localhost:19092', 'topic', 'consumer', 'JSONEachRow') SETTINGS kafka_keeper_path = '/clickhouse/{database}/kafka', kafka_replica_name = 'r1';

开发者：János Benjamin Antal。

新的 Kafka 引擎 🧪

CREATE TABLE ... ENGINE = Kafka( 'localhost:19092', 'topic', 'consumer', 'JSONEachRow') SETTINGS kafka_keeper_path = '/clickhouse/{database}/kafka', kafka_replica_name = 'r1';

启用新选项后，不再依赖 Kafka 跟踪偏移量，
而是自行通过 ClickHouse Keeper 管理。

如果插入尝试失败，将获取完全相同的数据块并重试插入，无论是网络故障还是服务器故障。

这使去重成为可能，令消费具有 恰好一次语义.

开发者：János Benjamin Antal。

开发者：Pavel Kruglov。

JSON 数据类型 🧪

工作原理：

— 分析 JSON，为每个路径推断数据类型。

— 将每个路径及每种不同类型保存为子列。

— 达到最大数量后，回退为
  将剩余路径一起保存。

这样可对任意
结构的 半结构化数据进行快速列式存储与查询!

开发者：Pavel Kruglov。

JSON 数据类型 🧪

如何插入：
— 使用 JSONEachRow 格式插入；
— 向 JSON 类型列插入包含 JSON 的字符串；
— 使用 JSONAsObject 格式插入，
  将整个对象放入 JSON 列；
— 从 String 转换为 JSON；

CREATE TABLE test (data JSON) ENGINE = Memory; INSERT INTO test VALUES ('{"a" : {"b" : 42}, "c" : [1, 2, 3]}'); INSERT INTO test FORMAT JSONEachRow {"data": {"a" : {"b" : 42}, "c" : [1, 2, 3]}}; SELECT data FROM test;

开发者：Pavel Kruglov。

JSON 数据类型 🧪

如何查询：
— 将特定路径读取为 Dynamic 列： SELECT data.a AS x, toTypeName(x) FROM test;
— 读取特定路径并 转换 为所需数据类型： SELECT data.a.b::UInt32 AS x, toTypeName(x) FROM test;
— 读取特定路径并 假定 其数据类型： SELECT data.a.b.:Int64 AS x, toTypeName(x) FROM test;
— 读取 子对象 作为 JSON： SELECT data.^a AS x, toTypeName(x) FROM test;

开发者：Pavel Kruglov。
