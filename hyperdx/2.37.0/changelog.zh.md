- 0558f77e：记录并显示评估的传送时间到达了哪个通知目标。 `webhookDurationMs` 是一个涵盖整个交付的数字，并且由于目标是同时调度的，最慢的目标会设置它 - 因此多目标警报报告的数字无法判断哪个 Webhook 负责，或者其他目标都很好。

每次评估而不是每次调度存储：通知 10 个目标的 50 组警报否则会将 500 个条目写入每个历史记录行。该数组的上限为“ALERT_NOTIFICATION_TARGETS_LIMIT”，并按最慢的顺序排序，因此该上限会删除最不感兴趣的行。在此更改之前写入的记录将继续呈现其总数，没有任何可扩展的内容。

- 8f3126f0：将指标资源管理器添加到图表编辑器中，这样您就不再需要知道指标的名称才能绘制图表。指标选择旁边的浏览控件会打开一个模式，该模式在指标名称空间上具有前缀层次结构 - “system” → “cpu” → “utilization” - 以及源报告的每个名称和描述的搜索。每行都包含指标的种类及其描述，详细信息窗格显示单位（从其 UCUM 代码呈现）、报告服务以及深入了解其值的标签键。以前，选择器是一个包含 3,000 个条目的扁平下拉列表，并且该元数据仅在您已经提交了指标后才会出现。 

名称按指标拆分：当名称有一个时在“.”上（OpenTelemetry），否则在“_”（Prometheus 导出器）上。在实践中，按名称而不是按源来决定很重要——真正的部署包含数千个下划线式收集器自遥测名称以及数十个点应用程序指标，并且单个源范围的分隔符会扁平化任何数量不足的系列。单子链崩溃，因此树不会成为走廊，并且未过滤的树永远不会被截断，因此任何命名空间都不会丢失。 

在浏览指标的标签时，您可以按照图表编辑器的内联属性面板允许的方式分级过滤器和分组；它们显示为可拆卸芯片并与公制一起应用。应用还可以设置适合该类型的聚合 - 仪表的平均值、计数器的总和、直方图的 p95 - 而不是继承之前系列使用的任何内容。两者都是替换而不是合并，因为它们是根据新选择的指标编写的：分阶段过滤器替换了系列条件，分阶段分组替换了图表的条件。 

图表编辑器的内联属性面板现在还显示指标的类型。仅列出可绘制图表的类型（仪表、总和、直方图、指数直方图）； `summary` 被省略，因为查询渲染器无法翻译它。浏览器是一个独立的组件，因此模式是它周围的一个外壳，而不是唯一可能的家。

- 3c81bb96：直接为警报的配置通道构建警报通知，而不是将它们编码为“@webhook-&lt;id&gt;”提及字符串并将其解析回来。该往返仅携带“type”和“webhookId”，并且它会在用户在消息正文中写入的任何内容之后附加通道 - 因此包含“MAX_NOTIFICATIONS_PER_EVENT”的正文提到消耗了每个事件上限的每个槽，并且警报自己配置的通道（它设置为通知的一个目标）从未悄悄到达。配置的通道现在首先排队，并且不受该上限的限制，这仅意味着限制临时提及； “channels”已受“MAX_ALERT_CHANNELS”限制。写入消息正文的提及未更改，仍然有上限，并且仍然针对配置的通道进行重复数据删除，因此命名一个通道两次会通知它一次。这还消除了通道无法携带超出其 webhook id 的任何字段进行传递的损耗，具有更丰富通道类型的下游分叉（例如“电子邮件”通道或也需要 Slack 通道 id 的 Slack 应用程序通道）无法解决这一问题。 `getDefaultExternalActions` 已被删除，因为不再需要配置通道的提及字符串形式。
