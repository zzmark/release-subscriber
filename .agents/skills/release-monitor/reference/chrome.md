# Chrome stable major release

Use for software/chrome.yaml when processing.release_unit is stable_major_version. The unit is one Chrome Stable major milestone such as 140, not a patch build or a Beta/Dev/Canary announcement.

## Discover and select

1. Start at selection.minimum_version, inclusive. Route by the configured version boundary: through `source.legacy_primary_through_version` (154), use `legacy_release_url_template`; from `source.primary_from_version` (155), use `release_url_template` (ChromeStatus). For every new milestone from 155, also check the legacy index and matching legacy version page. The old site remains a secondary source; its 404 does not disqualify a complete, verified ChromeStatus release. Do not rewrite existing 140–154 reports during this transition.
2. Inspect the major version, page-level channel/status, and date label. ChromeStatus can expose future notes with `Preview` and `Scheduled Stable Release`; existence, feature-level shipping status, or a scheduled date in the past is not proof of a Stable release. Beta/Dev/Canary notes are ineligible. A sparse/dynamic index or missing page is uncertainty, not evidence of no release; check consecutive major pages and official channel records.
3. Query `source.stable_releases_api_url_template` for the candidate milestone. Validate returned records: `channel == Stable`, `milestone == candidate`, version's major == candidate, and actual publication time is not in the future. Do not assume the server applied query filters. Windows Stable is the desktop verification baseline, not a claim about Android or every platform. A newest-Stable-only query can miss previous milestones; query each candidate explicitly. If the response hits its quantity limit, obtain complete history or corroborate the first release with an official Stable announcement before choosing a date.
4. Require agreement between actual Stable publication evidence and the release-note body's applicability. If the notes still say Preview/Beta while the API lists Stable, report a source conflict and hold publication pending an official Stable announcement and confirmation that the body applies to that Stable release. Do not relabel a preview or silently discard either source. A stable feature entry alone cannot resolve a page-level conflict.
5. Use the confirmed actual Stable first-release date in UTC. For legacy articles verify their `Stable release date`; for ChromeStatus cross-check the date against actual Stable history or the official Chrome Releases Stable announcement. API `time` is Unix milliseconds: use the earliest matching actual Stable release, not the latest patch timestamp. `Scheduled Stable Release`, last-updated dates, search timestamps, and task dates are never publication evidence on their own. If dates disagree, hold and report the gap.
6. Compare eligible majors with existing chrome/<major>/ directories. In scan results include both the body URL and Stable verification URL, observed page status/date label, and qualification or hold reason. A scan does not itself authorize new report files.

## Build each report

1. Fetch the official English body from the version-selected primary source. For the legacy site use `hl=en`; on ChromeStatus select English and verify the returned language. Omit account-specific `authuser` parameters. If the legacy page also exists from 155, cite it as supplementary and record any substantive disagreement rather than merging conflicting texts. Use the article body from its Chrome title through the release-note sections; exclude site navigation, account controls, related-content chrome, and footer.
2. Convert that body faithfully to Markdown in changelog.md. Preserve every substantive heading, paragraph, list, code sample, link, image, and caveat in source order. Use absolute official URLs for site-relative assets and links. Identify the official page as the source; the Markdown is a format conversion of the English article, not a separately published upstream Markdown file. Retain source and applicable license attribution in both language files: the legacy Chrome for Developers footer specifies CC BY 4.0 for text and Apache 2.0 for code; inspect ChromeStatus itself for its applicable terms rather than copying the legacy license claim onto the new source. Inspect the HTML against the converted Markdown for malformed inline markup that disappears during parsing and for invalid upstream links such as a `Spec` URL ending in `/None`; restore lost text and annotate an invalid upstream link without publishing it as a working URL.
3. Translate the complete converted article with ChatGPT into changelog.zh.md, preserving structure, links, code, identifiers, and feature availability qualifiers. The site's `hl=zh-cn` rendering is useful for comparison but is not the translation source for this repository.
4. Write index.md for the same major and the confirmed actual Stable first-release date. Summarize developer-impacting changes and real migration risks only. Some official articles mention features still limited to non-Stable channels; keep those caveats in both changelogs and do not present such features as already Stable in the summary.
5. Follow report-format.md to update the landing table, homepage, and checks. Only after the complete requested initial backfill is done should history.initial_backfill_status become completed. A shell without reports remains planned.

If an article cannot be read completely or its Stable status/date cannot be confirmed, hold that version and report the gap.
