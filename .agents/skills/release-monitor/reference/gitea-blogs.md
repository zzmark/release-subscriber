# Gitea official release blogs

Use alongside github-gitea.md and the product-specific reference when publishing Gitea server or Runner releases, or alone when supplementing blog links. Read the selected product config first.

1. Fetch releases and apply selection rules through github-gitea.md. The configured GitHub or Gitea Releases remain authoritative for tags, stability, publication dates and original bodies.
2. Browse the configured official blog index or source directory; follow pagination when present. Inspect the actual article, not search snippets. Select announcements for the exact product: server articles for Gitea, Runner articles for Gitea Runner. Exclude the other product and unrelated tutorials.
3. Match the announcement title and opening text to the exact product and version and verify its official Release link. Do not construct an unverified URL from a version. A later article may contain older Changelog sections; those are not independent release announcements for the older versions.
4. For a verified match, fetch the full official article (prefer its Markdown from the official gitea/blog repository). Translate the entire article to <slug>/<version>/blog.zh.md using ChatGPT. Preserve heading levels, list order, code blocks, inline code, links, remote images, upgrade notes, acknowledgements, and every historical Changelog section, even those below the monitored minimum. Do not substitute a summary or use machine translation. Identify the original authors, blog publication date, original article/source and license; mark the page as an unofficial Chinese translation and retain required attribution/license notices. Keep temporary original snapshots under .release-work.local/ for comparison.
5. Add release-blog-url (official article) and release-blog-zh-url="./blog.zh" to that version's ReleaseCard, and original/Chinese links in the landing page's 发布博客 column. The sidebar detects blog.zh.md. Keep the existing upstream release-url and UTC date unchanged. If no matching article is found, omit both props and use — in the table. An inaccessible article is uncertainty, not proof of absence; do not publish an empty or partial translation.
6. Check for newly published announcements for existing versions too. Supplementary blog translations and links are permitted by the product config without rewriting existing summaries or either Changelog. Keep blog text separate from changelog.md. For a scan-only request, report newly matched articles without editing files.
7. Compare original and translation section by section: paragraph/item counts, links, code spans and fenced code must correspond; review meaning and terminology manually. Run releases:sync-home, releases:check and docs:build. Verify both blog links in rendered cards, the landing table, and sidebar. The release check requires a complete local blog page whenever its card advertises a blog translation.
